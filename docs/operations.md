# 운영·장애 대응 안내

운영 사이트는 [kosmos-ashy.vercel.app](https://kosmos-ashy.vercel.app)에 배포됐다. 실제 Supabase 서울 프로젝트에는 최초 스키마를 설치하고 공개 회원가입과 익명 원고 접근을 차단했다. 작가 로그인·원고 저장·서버 변경 반영·첨부 업로드·샘플 공개를 확인했다. 다른 기기 첨부·충돌과 실제 ZIP 복원 시험은 남아 있다. 다음 절차는 로컬 사용과 연결 후 운영을 위한 기준이다. 복구 작업 전 가능한 최신 ZIP과 화면의 본문을 확보한다. 실제 비밀 키·원고를 오류 보고에 붙이지 않는다.

## 평소 확인할 것

- 기기를 바꾸기 전 **클라우드 동기화됨**인지 확인한다.
- 중요한 작업·환경 변경 전 ZIP을 다른 저장소에 보관한다. 자동 외부 백업이 연결될 때까지 수동 절차가 필요하다.
- 배포·의존성·DB 변경 전 기존 원고를 보존하고 시험 환경에서 확인한다.
- 운영 변경은 날짜·내용·검증 결과를 [변경 기록](../CHANGELOG.md)에 남긴다.
- 서비스 가격·사용량·첨부 용량·AI 호출은 연결한 제공자의 대시보드에서 확인한다. 현재 앱은 비용 대시보드를 제공하지 않는다.

## 충돌 처리

현재 선택은 **작업 공간 전체**에 적용된다. 부분 미리보기만 보고 특정 장면끼리 합쳐진다고 생각하지 않는다.

1. 열린 창을 유지하고 **양쪽 원고 백업 만들기 → 파일 저장**으로 ZIP을 확보한다. 실패하면 중요한 본문도 별도로 보관한다.
2. 선택 시 양쪽 원고가 복구 이력에 저장되는지 오류를 확인한다.
3. 사용할 작업본을 선택한다. 다른 쪽에서 필요한 문장은 이력·백업에서 확인해 수동으로 반영한다.
4. 새 복구 지점과 ZIP을 남기고 클라우드 저장을 확인한다.

전체 변경 비교와 수동 병합 UI는 [로드맵](roadmap.md)의 우선 보완 항목이다.

## 원고가 사라진 것처럼 보일 때

origin, 브라우저, 로그인 계정, namespace를 먼저 확인한다. `127.0.0.1`, `localhost`, 다른 포트, Vercel 주소, 사용자 도메인은 기기 저장 관점에서 서로 다를 수 있다.

이전 미리보기의 원고는 원래 브라우저·주소에서 열어 ZIP을 만든다. 서버 확인된 원고는 같은 Supabase 프로젝트·작가 계정으로 가져온다. 복구 이력과 외부 ZIP을 확인한 뒤 [복원 안내](backup-restore.md)를 따른다. 브라우저 데이터가 삭제되고 서버·ZIP에도 없던 수정은 앱이 복구할 수 있다고 보장하지 않는다.

## 배포 변경과 되돌리기

1. 정상 소스 버전·환경 변수 설정·DB 변경 번호를 기록한다. 값 자체는 비밀 관리 도구에 보관한다.
2. 원고·첨부를 백업하고 시험 환경에서 검사한다.
3. `pnpm typecheck`, `pnpm test`, `pnpm build`를 통과한 소스를 배포한다.
4. 작가 저장, 로그아웃한 독서, 비공개 접근 차단, 첨부, ZIP을 확인한다.
5. 문제 발생 시 검증된 이전 코드로 되돌린다. 이전 코드가 새 DB 형식과 호환되는지 먼저 확인한다.

코드 배포를 되돌리는 것은 DB·원고·공개판을 되돌리는 작업이 아니다. DB 복원은 별도 절차로 수행하고 현재 원고를 먼저 보관한다. `001_studio.sql`은 재설치용 반복 스크립트가 아니다. 이후 변경은 새 번호의 마이그레이션으로 추가한다.

## 검증 재현

자동 검사:

```powershell
pnpm typecheck
pnpm test
pnpm build
```

PGlite 테스트는 Auth·Storage·Realtime의 시험용 구조를 만들어 SQL을 실행한다. Supabase 실서비스 검증을 대신하지 않는다.

수동 브라우저 재현은 새 시험 브라우저·샘플 원고로 [검증 기록](../VERIFICATION.md)의 10개 흐름을 수행한다. 실제 원고에 테스트 문구를 쓰거나 테스트 복원을 실행하지 않는다. 1512px·360px은 기존 확인 폭이며 추가 기기·한글 IME·접근성·장편 성능은 별도 확인한다.

소스 ZIP에는 빌드 결과·의존성·키를 넣지 않는다. 정확한 설치는 lockfile로 재현한다. 문서 내부 링크와 코드 위치도 변경 때 확인한다.

## 운영 기록 항목

실서비스 연결 후 프로젝트 ID·URL·지역·운영 플랜, 배포 URL·코드 버전, 마이그레이션 적용일, 작가 허용 UUID, 마지막 백업 성공·복원 시험일, AI 모델·예산을 기록한다. 사용자 UUID·서비스 주소는 운영자가 정한 접근 범위에서 보관하며 공개 문서에 자동으로 복사하지 않는다.

Supabase는 서울 지역의 기존 Free 프로젝트를 사용하고 2026-10-01에 최초 SQL을 적용했다. 프로젝트 연결 값은 작업용 설정에만 보관하며 공개 문서·소스 ZIP에는 키와 사용자 UUID를 넣지 않는다. Vercel 첫 운영 배포는 소스 `ef19083d5784c09d1bb4dc5e7f9d075f3bfa978a`로 46초에 Ready가 됐다. Supabase 변수는 Production에만 설정했다. 작가 로그인·기본 저장 시험은 완료했고 독립 백업·실제 ZIP 복원과 AI 설정은 미완료다. 운영 브라우저에서 ZIP 생성 메시지는 확인했으나 도구가 다운로드 파일을 전달하지 않아 파일 검증은 수행하지 못했다. 일반 브라우저에서 ZIP을 실제 내려받고 별도 시험 환경에서 복원해야 한다. 모니터링, 자동 백업 실패 알림, 공개 철회·관리 UI도 후속 범위다.

## 새 연결 운영 점검

Drive는 [연결 절차](service-connection.md) 후 최초 실제 ZIP 검증·복원과 다음 04시대 실행을 확인한다. 앱의 마지막 성공 시각이 갱신되지 않으면 Vercel cron 로그·OAuth 취소/만료·공간을 확인한다. 자동 실패 알림은 없다. 실패 시 기존 정상 파일을 지우지 않는다. 백업 보관량은 사용자가 직접 관리하며 유료 저장 공간은 자동 구매하지 않는다.

AI는 선택한 제공자의 키·모델을 함께 설정한다. 세 제공자 공통 10회/일 제한, 제공자 자체 사용 제한·예산을 확인한다. 키를 바꾼 뒤 재배포하며 로그에 원고·키·토큰을 남기지 않는다. 변환 오류는 원본 파일과 경고를 보관해 작은 묶음으로 재현한다.
